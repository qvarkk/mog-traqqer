# go-fiber-template

A backend template for Go services, split into two processes that communicate
over gRPC:

- **`gateway`** — the public HTTP API, built with [Fiber v3](https://docs.gofiber.io/).
  It owns no business rules: it translates HTTP into gRPC calls.
- **`users`** — a gRPC-only microservice that owns the users business logic and
  the PostgreSQL database.

Both share [Uber FX](https://uber-go.github.io/fx/) for dependency injection and
lifecycle, [zap](https://github.com/uber-go/zap) for structured logging, pgx v5
with SQL generated by [sqlc](https://sqlc.dev/) and migrations applied by
[goose](https://github.com/pressly/goose). Each ships as a `scratch` Docker image
built and published by GitHub Actions.

The point of the template is the *wiring*: how two services are composed, how
configuration reaches them, how errors cross the gRPC boundary and become HTTP
responses, and how each process starts and stops cleanly. Replace the business
logic, keep the skeleton.

## Requirements

| Tool | Version | Notes |
|---|---|---|
| Go | 1.27+ | `go.mod` declares `go 1.27.0` |
| PostgreSQL | 14+ | 18 is what the compose file pins; `gen_random_uuid()` needs 13+ |
| Docker | any recent | for the local stack and for building the images |
| sqlc | 1.31+ | only needed when you change the schema or the queries |
| buf | 1.74+ | only needed when you change the `.proto` files. Ships its own compiler, so `protoc` is not required. |
| grpcurl | any | optional, for calling the users service by hand |
| GNU Make | optional | `make` targets are convenience wrappers |

## Quick start

```bash
docker compose up --build
```

This starts PostgreSQL, the `users` service and the `gateway`. The gateway
serves on `http://localhost:3000`, and the users service's gRPC port is published
on `localhost:9090` so grpcurl can reach it during development.

```bash
curl localhost:3000/healthz
# {"status":"ok"}

curl -X POST localhost:3000/api/v1/users \
  -H 'Content-Type: application/json' \
  -d '{"email":"ada@example.com","display_name":"Ada Lovelace"}'
# {"id":"...","email":"ada@example.com",...}
```

To run the two services on the host instead (useful for fast rebuilds), start
only PostgreSQL and run each process in its own terminal:

```bash
docker compose up -d postgres

cd backend
cp .env.example .env      # optional: the defaults match docker-compose
go run ./cmd/users        # terminal 1
go run ./cmd/gateway      # terminal 2
```

Migrations run during the users service's startup, so the schema exists after
its first boot.

## Architecture

```
                 HTTP :3000                    gRPC :9090
  browser ───▶ gateway ─────────────────────▶ users ────▶ PostgreSQL
              (Fiber)      UserServiceClient   (grpc)       (pgx + goose + sqlc)
```

- The **gateway** binds HTTP, negotiates the request language, and forwards each
  request to the users service over gRPC. It has no database connection and no
  validation rules of its own.
- The **users** service owns the users domain: validation, pagination, and the
  database. It exposes `user.v1.UserService` plus the standard gRPC health
  service.

The contract between them is the `.proto` file. The generated client is what the
gateway compiles against; the generated server is what the users service
implements. This is why the generated code lives in `gen/`, not `internal/` — see
[gRPC](#grpc).

## Configuration

All configuration comes from environment variables. A `.env` file is loaded as a
convenience for local development only — real environment variables always take
precedence, and a missing `.env` is not an error.

The two services share one config struct but each reads a subset:

- **gateway** reads `APP_*`, `LOG_*`, `HTTP_*`, `USERS_*`, `I18N_*`.
- **users** reads `APP_*`, `LOG_*`, `GRPC_*`, `DB_*`.

### Application (both services)

| Variable | Default | Description |
|---|---|---|
| `APP_ENV` | `development` | `development`, `staging` or `production`. Controls log format: human-readable in development, JSON everywhere else. |
| `APP_NAME` | `go-fiber-template` | Application name, used in logs and the Fiber app name. |
| `LOG_LEVEL` | `info` | `debug`, `info`, `warn`, `error`, `dpanic`, `panic`, `fatal`. |
| `LOG_FILE` | *(empty)* | Optional. Empty logs to stdout only — what containers want. When set, logs are **also** written there as rotated JSON. |

### HTTP server (gateway)

| Variable | Default | Description |
|---|---|---|
| `HTTP_HOST` | `0.0.0.0` | Interface to bind. |
| `HTTP_PORT` | `3000` | Port to bind. |
| `HTTP_READ_TIMEOUT` | `10s` | Bound on reading a full request. |
| `HTTP_WRITE_TIMEOUT` | `10s` | Bound on writing a response. |
| `HTTP_IDLE_TIMEOUT` | `60s` | How long an idle keep-alive connection stays open. |
| `HTTP_SHUTDOWN_TIMEOUT` | `10s` | How long in-flight requests get to finish on shutdown. |
| `HTTP_BODY_LIMIT` | `4194304` | Maximum request body size in bytes (4 MiB). |
| `HTTP_CORS_ALLOWED_ORIGINS` | `*` | Comma-separated allowed origins. Use explicit origins in production. |

### Users service client (gateway)

| Variable | Default | Description |
|---|---|---|
| `USERS_ADDR` | `localhost:9090` | Where the gateway dials the users service. In docker-compose this is `users:9090`. |

### gRPC server (users service)

| Variable | Default | Description |
|---|---|---|
| `GRPC_ENABLED` | `true` | Start the gRPC listener. Off means the server is constructed but never served. |
| `GRPC_HOST` | `0.0.0.0` | Interface to bind. Bind a private interface in production. |
| `GRPC_PORT` | `9090` | Port to bind. |
| `GRPC_REFLECTION_ENABLED` | `true` | Let tools like grpcurl discover the API. Advertises the whole surface, so turn it off in production. |
| `GRPC_SHUTDOWN_TIMEOUT` | `10s` | Bound on the graceful drain before a forced stop. |
| `GRPC_CONNECTION_TIMEOUT` | `10s` | Bound on establishing a connection. |
| `GRPC_MAX_RECV_MSG_SIZE` | `4194304` | Maximum received message size in bytes. |
| `GRPC_MAX_SEND_MSG_SIZE` | `4194304` | Maximum sent message size in bytes. |

### Database (users service)

| Variable | Default | Description |
|---|---|---|
| `DB_URL` | *(empty)* | A complete connection string. When set, every other `DB_*` value is ignored. Never logged. |
| `DB_HOST` | `localhost` | Database host. |
| `DB_PORT` | `5432` | Database port. |
| `DB_USER` | `postgres` | Database user. |
| `DB_PASSWORD` | `postgres` | Database password. |
| `DB_NAME` | `app` | Database name. |
| `DB_SSL_MODE` | `disable` | `disable`, `allow`, `prefer`, `require`, `verify-ca`, `verify-full`. Correct for a local database and for nothing else. |
| `DB_MAX_CONNS` | `10` | Pool ceiling. Keep `DB_MAX_CONNS × replicas` under the server's `max_connections`. |
| `DB_MIN_CONNS` | `1` | Idle connections kept warm. |
| `DB_MAX_CONN_LIFETIME` | `1h` | Recycle connections rather than holding them open forever. |
| `DB_MAX_CONN_IDLE_TIME` | `30m` | How long an unused connection is kept. |
| `DB_CONNECT_TIMEOUT` | `5s` | Bounds the startup connection and ping. |
| `DB_AUTO_MIGRATE` | `true` | Apply the embedded migrations during startup. |

If your platform hands out a single connection string, set `DB_URL` to it and
leave the rest alone:

```bash
DB_URL='postgres://user:pass@host:5432/db?sslmode=require'
```

Invalid values fail fast: `APP_ENV=nonsense`, `DB_SSL_MODE=sort-of` or
`DB_MAX_CONNS=0` stops the process at startup with a clear error instead of
failing on the first request.

### Internationalisation (gateway)

| Variable | Default | Description |
|---|---|---|
| `I18N_DEFAULT_LANGUAGE` | `en` | Used when a request expresses no usable preference. Must have a catalog, or startup fails. |
| `I18N_QUERY_PARAM` | `lang` | Per-request override, e.g. `?lang=ru`. |
| `I18N_COOKIE_NAME` | `lang` | Per-user preference, used when the query parameter is absent. |

The available languages are **not** listed here: they are discovered from the
catalog files in `internal/i18n/locales`, so the two cannot drift apart.

### How variable names are derived

The name is the section name and the field name joined by an underscore:

```
App.Env      ->  APP_ENV
HTTP.Port    ->  HTTP_PORT
DB.MaxConns  ->  DB_MAX_CONNS
Users.Addr   ->  USERS_ADDR
```

Multi-word fields need the `split_words:"true"` struct tag, otherwise no
underscores are inserted (`DB.ReadTimeout` would become `DB_READTIMEOUT`).

Do **not** add `envconfig:"..."` tags to leaf fields. The parser treats such a tag
as an alternative name and falls back to it, so `envconfig:"NAME"` on `App.Name`
would make a bare `NAME` variable — which many systems set to the current user —
silently override the real setting, and a bare `PORT` would shadow `HTTP_PORT`.

## Endpoints

The gateway serves these HTTP routes:

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/healthz` | Liveness. Does **not** touch dependencies. |
| `GET` | `/readyz` | Readiness. Checks the users service; returns 503 while it is unreachable. |
| `GET` | `/api/v1/ping` | Example endpoint; echoes the request ID. |
| `POST` | `/api/v1/users` | Create a user. |
| `GET` | `/api/v1/users?limit=&offset=` | List users, newest first. `limit` defaults to 20, max 100. |
| `GET` | `/api/v1/users/:id` | Fetch one user. |
| `PATCH` | `/api/v1/users/:id` | Change a display name. |
| `DELETE` | `/api/v1/users/:id` | Delete a user. Returns 204. |

The users service exposes these RPCs on `GRPC_PORT` (default 9090):

| RPC | Purpose |
|---|---|
| `user.v1.UserService/CreateUser` | Create a user. |
| `user.v1.UserService/GetUser` | Fetch one user. |
| `user.v1.UserService/ListUsers` | List users, newest first. |
| `user.v1.UserService/UpdateUser` | Change a display name. |
| `user.v1.UserService/DeleteUser` | Delete a user. |
| `grpc.health.v1.Health/Check` | The standard gRPC health probe. |

Liveness and readiness are deliberately different. A failing dependency must make
the gateway *unready* so traffic stops being routed to it, but it must not make
it *unhealthy*, or the orchestrator would kill and restart a process that is
working perfectly well.

Every request gets a request ID, reused from an incoming `X-Request-ID` header
when it is valid and generated otherwise. It is returned in the `X-Request-Id`
response header and in every error body.

## Error responses

Every gateway failure uses one envelope, so clients only parse one shape:

```json
{
  "error": {
    "code": "not_found",
    "message": "Not Found",
    "request_id": "X-DLjF1hNPouTFsGuVRZ8tRTLUSFHbaNl4tWD3XQlWE"
  }
}
```

`code` is stable and machine-readable — branch on it, and it is never
translated. `message` is for humans and is translated for the request's language
(see [Internationalisation](#internationalisation)). For 5xx responses the
message is replaced with the status text and any `details` are dropped, so
internal addresses and causes cannot leak; the real cause is logged with the
same request ID.

Errors originate in the users service as gRPC status codes, each carrying a
stable machine reason via `google.rpc.ErrorInfo`. The gateway maps the status
code onto the HTTP status and the reason onto the envelope `code`:

| gRPC code | HTTP status |
|---|---|
| `INVALID_ARGUMENT` | 422 (validation) or 400 (bad id, bad page) |
| `NOT_FOUND` | 404 |
| `ALREADY_EXISTS` | 409 |
| `PERMISSION_DENIED` | 403 |
| `UNAUTHENTICATED` | 401 |
| `UNAVAILABLE`, `DEADLINE_EXCEEDED` | 503 |
| anything else | 500 |

Validation failures carry a `details` object naming each offending field:

```json
{
  "error": {
    "code": "validation_failed",
    "message": "the request contains invalid fields",
    "details": {
      "fields": { "email": "this must be a valid email address" }
    }
  }
}
```

The per-field message is translated by the gateway using a key the users service
sends alongside each violation, so field errors stay localisable without the
gateway knowing the validation rules.

```
│   │   ├── grpcserver/              gRPC server, interceptors, lifecycle, status helpers (users)
│   │   ├── i18n/                    catalogs, language negotiation, per-request localizer (gateway)
│   │   │   └── locales/             en.json, ru.json — add a file to add a language

│   │   │   ├── migrations/          the schema, applied by goose and read by sqlc
│   │   │   ├── queries/             hand-written SQL, compiled by sqlc
│   │   │   └── dbgen/               generated query layer (committed)
│   │   ├── user/                    the users service: service.go (rules) + grpc.go (adapter)
│   │   └── gateway/                 the HTTP gateway: client.go + handler.go (adapter)

│   ├── buf.yaml / buf.gen.yaml      buf configuration

```

`internal/` is enforced by the Go toolchain: nothing outside this module can
import it. `gen/` is the deliberate exception — the generated protobuf client is
the contract the gateway compiles against, so it must stay importable.

## How it works

Each `main.go` does almost nothing. It lists the modules and hands control to
FX, which constructs everything, runs `OnStart` hooks in order, waits for
`SIGINT`/`SIGTERM`, then runs `OnStop` hooks in **reverse** order.

The users service:

```go
fx.New(
    config.Module,
    logger.Module,
    db.Module,        // before grpcserver: the pool must close *after* the listener
    grpcserver.Module,
    user.Module,
    fx.Invoke(reportStartup),
).Run()
```

The gateway:

```go
fx.New(
    config.Module,
    logger.Module,
    i18n.Module,
    gateway.Module,
    server.Module,
    fx.Invoke(reportStartup),
).Run()
```

### Lifecycle ordering

FX starts `OnStart` hooks in construction order and stops `OnStop` hooks in the
reverse order. The module order above is chosen so that, on shutdown, the
listener stops first and the thing it depends on (the database pool, or the
gRPC client connection) is closed after the listener has drained.

- In `users`, `db.Module` is listed before `grpcserver.Module`, so the pool
  closes after the gRPC listener stops.
- In `gateway`, the HTTP server's constructor depends on the readiness prober,
  which the gateway builds from its gRPC client. That dependency forces the
  client to be constructed first, so the connection closes after the HTTP
  listener has drained.

### Middleware order (gateway)

```
cors → request id → language → access log → recover
```

The access log sits outside `recover` so a panic still unwinds through it and is
logged. The language is resolved before the access log because the access log is
what turns errors into responses and needs the language already set.

### Startup and shutdown

Migrations run during the users service's FX construction, not in an `OnStart`
hook. FX runs every constructor and `fx.Invoke` before any `OnStart` hook, so the
schema is guaranteed ready before a single request is served.

On shutdown, both services drain gracefully: the gateway waits for in-flight HTTP
requests, the users service reports `NOT_SERVING` to its gRPC health service and
then drains, and the database pool closes last of all.

## Working with the database

The database is owned entirely by the users service. The gateway never opens a
connection.

### The schema lives in one place

`internal/db/migrations/*.sql` is applied by goose **and** read by sqlc:

```yaml
# sqlc.yaml
schema:  internal/db/migrations
queries: internal/db/queries
```

So the schema has a single source of truth: add a migration and the columns are
immediately visible to the query layer.

### Migrations

```bash
cd backend
# add internal/db/migrations/00002_xxx.sql with -- +goose Up / -- +goose Down
make sqlc-check     # confirm the query layer still matches
```

Migrations are embedded in the binary, applied at startup when
`DB_AUTO_MIGRATE=true`, and serialised with a Postgres advisory lock so several
replicas can boot at once without racing. Set `DB_AUTO_MIGRATE=false` once
migrations become a separate deployment step.

### The query layer

`internal/db/queries/*.sql` holds hand-written SQL. `make sqlc` turns it into the
type-safe functions in `internal/db/dbgen`, plus a `Querier` interface that the
users service's `Service` depends on:

```go
type Service struct {
    queries dbgen.Querier
}
```

## Internationalisation

Internationalisation lives in the gateway, because it is an HTTP concern: the
language is negotiated per request from the query parameter, cookie and
`Accept-Language` header.

Catalogs live in `internal/i18n/locales/<tag>.json`, are embedded with
`//go:embed`, and are parsed at startup. **The set of supported languages is
discovered from those files**, so supporting a new language means adding a file
and restarting — no config change, no list to keep in sync.

```json
{
  "validation.email": "укажите корректный адрес электронной почты",
  "error.user_not_found": "пользователь с таким идентификатором не найден"
}
```

### Choosing the language

Per request, in this order — the first match wins:

1. the `?lang=` query parameter
2. the `lang` cookie (only consulted when the query parameter is absent)
3. the `Accept-Language` header, resolved with `golang.org/x/text`'s matcher, so
   `ru-RU,ru;q=0.9,en;q=0.8` picks Russian and `en-GB` picks English
4. `I18N_DEFAULT_LANGUAGE`

An unsupported language is not an error: the header is a preference list, so
`de-DE` falls back to the default rather than failing the request. The resolved
language is echoed in the `Content-Language` response header.

### Translating errors

The envelope's **`code` is never translated** — clients branch on it, so it must
stay stable. Only `message` and the validation `details` are localised.

The translation key is derived from the code: `user_not_found` is looked up as
`error.user_not_found`. Because the code now travels over gRPC as
`ErrorInfo.reason`, any error in the users service becomes translatable by adding
one catalog entry — no handler change in either service:

```bash
curl 'localhost:3000/api/v1/users/…?lang=ru'
# {"error":{"code":"user_not_found",
#           "message":"пользователь с таким идентификатором не найден", …}}
```

Field-level validation messages work the same way: the users service sends each
violation's translation key and English fallback, and the gateway translates it.

### Translating incrementally

Every lookup carries an English fallback, and a message with no catalog entry is
served verbatim rather than leaking a raw message key:

```bash
curl 'localhost:3000/api/v1/users?limit=999&lang=ru'
# {"error":{"code":"invalid_limit","message":"limit must be between 1 and 100", …}}
```

You can ship English-only messages today and translate one at a time.

## gRPC

`proto/user/v1/user.proto` is the contract between the two services. `buf
generate` produces the client and server into `gen/user/v1`, and both are
committed.

### Why the generated code is not under internal/

`gen/` sits at the module root deliberately. Go forbids importing anything under
`internal/` from outside the module, and the generated *client* is exactly what
the gateway compiles against:

```go
import userv1 "github.com/qvarkk/go-fiber-template/backend/gen/user/v1"
```

Generating into `internal/gen` would compile fine here and make the contract
unusable everywhere else.

### The worked example

`internal/user` is the users service. Its `Service` owns all the rules —
validation, pagination bounds, and mapping `pgx.ErrNoRows` to `NOT_FOUND` and a
unique-violation to `ALREADY_EXISTS` — and its `GRPCHandler` is a thin adapter
that parses requests, calls the service and builds the response message.

`internal/gateway` is the other side of the wire: `client.go` dials the users
service, and `handler.go` binds JSON, calls the client, and maps the result onto
the HTTP envelope. It duplicates no business logic.

### The error contract

The users service returns standard gRPC status codes and attaches:

- `google.rpc.ErrorInfo.reason` — the stable machine code (`user_not_found`,
  `email_taken`, `validation_failed`, …), which the gateway turns into the HTTP
  envelope's `code`.
- `google.rpc.BadRequest` — for validation failures, the offending fields, with
  each field's translation key carried in `ErrorInfo.metadata`.

A gRPC status error cannot wrap a cause the way a Go error can, so
`grpcserver.Err` logs the underlying database error on the users service's side
before returning the status. The gateway then logs the upstream failure when it
renders the 5xx.

### Interceptors

```
access log → recover
```

The logging interceptor sits **outside** the recovery one, so a recovered panic
is still logged with its status code instead of unwinding past it. Panics become
`INTERNAL`, and the panic value and stack go to the log, never to the client.
The cause is only logged at error level when the failure is the service's own; a
`NOT_FOUND` is the caller's problem and should not flood the error log.

### Health and reflection

The users service registers two standard services:

- **`grpc.health.v1.Health`** — what `grpc_health_probe` and Kubernetes gRPC
  readiness probes call. It reports `SERVING` on startup and flips to
  `NOT_SERVING` *before* draining, so a load balancer stops routing here while
  in-flight calls finish.
- **`grpc.reflection.v1.ServerReflection`** — lets grpcurl discover the API
  without a local copy of the `.proto` files. Advertises the whole surface, so
  turn it off with `GRPC_REFLECTION_ENABLED=false` in production.

The gateway's `/readyz` is a gRPC health check against the users service, so it
reports ready exactly when its upstream is reachable.

```bash

```


### Changing the API

```bash
cd backend
# 1. edit proto/user/v1/user.proto
make proto-lint   # buf lint
make proto        # buf generate
```

`buf` ships its own compiler, so `protoc` is never needed — only the two
generator plugins, which is what CI installs. CI runs `buf lint`, then
`buf generate` followed by `git diff --exit-code -- gen`, so a `.proto` change
without regenerated code fails the build.

Adding an RPC is a non-breaking change on the server side: every generated server
embeds `UnimplementedUserServiceServer`, so a new method answers `Unimplemented`
until you write it instead of failing to compile.

## Adding a feature

The `users` resource is the reference. To add, say, `orders`:

1. **Contract** — add `order/v1/order.proto` under `proto/`, `make proto`.
2. **Migration** — `internal/db/migrations/00002_orders.sql` with `-- +goose Up`
   and `-- +goose Down`.
3. **Queries** — `internal/db/queries/orders.sql`, one `-- name: ...` block per
   statement, then `make sqlc`.
4. **Service** — `internal/order/service.go`: the rules, depending on
   `dbgen.Querier`, returning `grpcserver.Err` / `grpcserver.InvalidArgument`.
5. **gRPC adapter** — `internal/order/grpc.go`: parse, call the service, build
   the response.
6. **Module** — `internal/order/module.go`: provide the service and handler,
   register the server. Add it to `cmd/users/main.go`.
7. **HTTP adapter** — `internal/gateway`: add handlers that call the generated
   client and map the result with `fromGRPC`, and register the routes in
   `registerRoutes`. Add nothing to `cmd/gateway/main.go` (the gateway module
   already wires the client and routes).

## Making it yours

The template still carries placeholder names. To rename:

1. Change the module path in `backend/go.mod` and update the imports
   (`go mod edit -module github.com/you/your-service` then `go mod tidy`), plus
   the `go_package` option in every `.proto` file.
2. Change `APP_NAME`'s default in `internal/config/config.go`.
3. Change the image name in `.github/workflows/backend.yaml`.
4. Replace the `users` feature with your own, then `make sqlc` and `make proto`.

If you keep the module path but rename the proto package, remember that
`buf.yaml` lints for the directory and package matching — `make proto-lint` will
tell you if they drift.

## Docker

One `Dockerfile` builds both binaries and a `SERVICE` build arg picks which one
goes into the image:

```bash
cd backend
make docker-build
```

Each image is a static binary on `scratch`: no shell, no package manager, roughly
the size of the binary plus certificates. It runs as a non-root user (`appuser`,
UID 65532).

Two consequences of `scratch` are worth knowing:

- **CA certificates are copied in explicitly.** Without them every outbound HTTPS
  request fails with `x509: certificate signed by unknown authority`, including
  `sslmode=verify-full` connections to PostgreSQL.
- **There is no shell**, so a `HEALTHCHECK` cannot run `curl`. Point your
  orchestrator at the gateway's `GET /healthz` / `GET /readyz`, and the users
  service's `grpc.health.v1.Health/Check`.

Because migrations are embedded, the users image contains everything it needs to
bring a database up to date.

The containers log to **stdout only**, and `/app` is not writable by `appuser`.
If you set `LOG_FILE`, mount a writable volume for it first.

## Continuous integration

`.github/workflows/backend.yaml` is a single pipeline with two jobs:

1. **Verify** — `go mod tidy` diff, `sqlc diff`, `buf lint`, a generated-code diff
   for both `dbgen/` and `gen/`, `go mod verify`, build, `go vet`, `staticcheck`.
2. **Build and push images** — runs only after Verify passes (`needs: verify`),
   so a broken commit can never publish an image. It builds both `users` and
   `gateway` for `linux/amd64` and `linux/arm64`, and pushes to GHCR on `push`.

Both code generators are checked the same way: if the input changed and the
generated output did not, the build fails rather than shipping code that
disagrees with its source.

Images are tagged with the commit SHA, the branch, `latest` on the default
branch, and semver tags for `v*` releases.

One gotcha: because the workflow sets a `paths` filter *and* a tag filter, a
release tag only builds an image if the tagged commit touched `backend/`. Remove
the `paths` filter if you want every tag to build.

## Not included yet

This template deliberately stops short of a few things. They are the natural next
steps rather than oversights:

- **Observability** — metrics and tracing, plus query-level timing. The gateway's
  `/readyz` checks only that the users service answers; the users service's own
  health service reports the process, not its database.
- **Auth** — there is no authentication or authorisation anywhere. Neither
  transport authenticates its callers, and the gRPC listener has no interceptors
  for mTLS or tokens.
- **gRPC streaming** — only unary RPCs are wired up, so there are no stream
  interceptors and no graceful handling of long-lived streams beyond the
  shutdown timeout.
- **Pagination by cursor** — `limit`/`offset` is fine for a template but degrades
  on large tables.
- **Row-level soft deletes, auditing, and connection-level timeouts** — none of
  the usual production hardening beyond what is listed above.
